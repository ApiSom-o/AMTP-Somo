# รายงาน: ปรับโค้ดตรวจ Merkle ให้เร็วขึ้น และแก้ลูปซ้อนที่เหลือใน Validator — 15 พ.ย. 2026

## สรุป

- ตรวจผล query เร็วขึ้น **1.25×** และ end-to-end เร็วขึ้น **1.2×** (วัดบน Mac)
- **hash ทุกตัว จำนวน hash ขนาด proof และผล accept / reject เหมือนเดิมทุกตัว**
- ไม่ได้ลดจำนวน hash และไม่ได้เปลี่ยน protocol

## ปัญหาที่เจอ

profile การตรวจ query จริง 120 ตัว (D1, N = 100,000) บน Mac:
- เวลาส่วนใหญ่อยู่ที่ `H()` ซึ่งถูกเรียกผ่าน `node_hash` / `leaf_hash` และ `root_from_proof`
- `node_hash` ของ AMTP เรียก `H()` แบบทั่วไป: แปลงชนิดข้อมูลทุกส่วน แล้ว `update` หลายครั้ง ใช้ 0.82 µs ต่อครั้ง ขณะที่ SE-COLLAB เรียก `sha256` ครั้งเดียว ใช้ 0.40 µs
- `root_from_proof` ใช้ `sorted(set)` ใหม่ทุกชั้นของ tree

## แก้อะไร

| ไฟล์ | เปลี่ยนอะไร |
|---|---|
| `amtp/core/merkle.py` `leaf_hash`, `node_hash` | ถ้า input เป็น bytes: สร้าง byte string แบบเดียวกับที่ `H()` สร้าง (length prefix ‖ tag ‖ length prefix ‖ ข้อมูล) แล้วเรียก `sha256` ครั้งเดียว และนับ `HashCounter` เท่ากับที่ `H()` นับ ถ้าไม่ใช่ bytes ส่งไปให้ `H()` เหมือนเดิม |
| `amtp/core/merkle.py` `root_from_proof` | เรียงลำดับครั้งเดียว แล้วจับคู่ไล่ไปทีละชั้น ใช้ sibling จาก proof ตามลำดับเดิมทุกตัว และยัง reject proof ที่สั้นหรือยาวเกินเหมือนเดิม |
| `amtp/validator.py` | แก้ลูปซ้อน 3 จุด (ดูหัวข้อถัดไป) |

**ลองแล้วไม่เอา:** เปลี่ยน `H()` ให้ต่อ bytes ทั้งหมดก่อนแล้ว hash ครั้งเดียว วัดแล้วแทบไม่เร็วขึ้น (0.73 → 0.69 µs) และช้าลงเล็กน้อยเมื่อข้อมูลใหญ่ จึงคืนเป็นโค้ดเดิม

## ลูปซ้อนที่เหลือใน Validator

- ไล่ทุกไฟล์ใน `amtp/` ด้วย script (AST) หา `x in <list>` ที่อยู่ในลูป และลูปที่ซ้อนกันแบบไม่ขึ้นต่อกัน แล้วอ่านทุกจุดที่เจอด้วยตา
- ทุกจุดที่แก้ เปลี่ยนแค่วิธีหา (list → set หรือ dict) ผลออกมาเหมือนเดิมทุกตัว

| บรรทัด (เดิม) | ปัญหา | แก้ |
|---|---|---|
| `_imt_root`: `h in added` | `added` เป็น list ทำให้วนเป็น (key ในหลักฐาน) × (key ใหม่) **ตรงกับที่เพื่อนเจอ** | ใช้ `added_set` |
| `gone = {... if p not in new_p}` | `new_p` เป็น list | ใช้ `new_set` |
| `... p in new_p` ในลูป `for j in range(n_sel + 1)` | `new_p` เป็น list | ใช้ `new_set` |
| `for p in fresh if ins[p] == j` ในลูป `for j in range(n_sel + 1)` | วน (n_sel) × (partition ใหม่) | จัดกลุ่ม `fresh` ตามจุดแทรกครั้งเดียว ลำดับเหมือนเดิม |

จุดอื่นที่ script เจอเป็น dict / set อยู่แล้ว หรือวนครั้งเดียวแล้ว `break` หรือวนแค่กุญแจของ owner ไม่กี่ตัว

## หลักฐานว่าผลไม่เปลี่ยน

- `tests/test_fast_hash_paths.py` (ใหม่, 114 test) เก็บโค้ดเดิมไว้เป็นตัวเทียบแบบคำต่อคำ แล้วเทียบ **digest, จำนวน hash, จำนวน byte ที่ hash และ error** ในกรณีต่อไปนี้
  - input สุ่มทุกชนิด: bytes ขนาดต่างๆ, str, int, bool, None, float, bytearray และ subclass ของ bytes
  - multiproof ที่ถูกต้อง
  - multiproof ที่ถูกแก้: ตัด, เติม, สลับลำดับ, เปลี่ยน sibling, leaf ผิด, ตำแหน่งเกิน, ตำแหน่งที่เป็น padding
  - input ขอบ: ว่าง, size 1, ตำแหน่งติดลบ, ตำแหน่งที่เป็น bool หรือ float
  - `multiverify` ทั้งชุด
- **ลองใส่บั๊กเพื่อดูว่า test จับได้** (คืนโค้ดแล้วทุกครั้ง)
  - สลับลำดับ sibling → fail 54 test
  - นับ byte ผิด 1 → fail 74 test
  - ไม่เช็ก proof ที่เหลือ → fail 46 test
- pytest ทั้งชุด **333 test ผ่าน** ทั้งโหมดปกติและ `AMTP_GAMMA_V=0`
  - รวม test end-to-end ของ Validator ที่เทียบกับโค้ดเดิม (`test_validator_imt_checks.py`)
  - รวม test การโจมตีทุกแบบ
- **A/B บน query จริง:** ด้านล่าง hash_verify, hash_server, proof_bytes และ rQ ตรงกันทุก query

## ผล update / Validator (Mac, ex3, N = 100,000, b = 1000)

คำสั่ง: `bench.experiments exp3 --sizes 100000 --batches 1000 --reps 1 --warmup 0` ใช้คำสั่งเดียวกับที่วัดหลัง PR #11

| | ก่อนแก้ลูปเลย | หลัง PR #11 | หลัง PR #16 (รอบนี้) | PR #11 → #16 |
|---|---|---|---|---|
| **Validator, insert** | 401 s | 27.6 s | **14.6 s** | **1.9×** |
| Validator, delete | 468 s | 16.6 s | 14.7 s | 1.13× |
| server, insert | — | 24.0 s | 20.5 s | 1.17× |
| server, delete | — | 25.9 s | 20.6 s | 1.26× |
| **update ทั้งหมด, insert** | 486 s | 51.8 s | **35.2 s** | **1.47×** |
| update ทั้งหมด, delete | 552 s | 42.6 s | 35.3 s | 1.21× |

- **insert เร็วขึ้นมากที่สุด** เพราะแก้ `h in added` (ลูปซ้อนที่เพื่อนเจอ) ตอนนี้ Validator ของ insert กับ delete เท่ากันแล้ว (14.6 กับ 14.7 s) ซึ่งควรเป็นแบบนี้ เพราะงานของสองฝั่งพอๆ กัน
- delete และ server เร็วขึ้นด้วย เพราะ `node_hash` ตัวใหม่ (server ใช้ตอนอัปเดต Merkle tree และ Validator ใช้ตอนตรวจ)
- **จำนวน hash ระหว่างรอบต่างกันเล็กน้อย** (13,521,410 กับ 13,521,388) แต่ไม่ได้มาจากการแก้โค้ด ลองรันซ้ำที่ N = 10,000, b = 100 โค้ดละ 2 รอบ:

| | รอบ 1 | รอบ 2 |
|---|---|---|
| โค้ดเก่า (a131032) | 1,283,406 | 1,283,634 |
| โค้ดใหม่ | 1,283,596 | 1,283,577 |

  โค้ดเก่าเองรันสองรอบก็ได้ไม่เท่ากัน จำนวน hash ของ update จึงขยับตามความสุ่มของแต่ละรอบ ส่วนที่ต้องเหมือนเดิมทุกตัวจริงๆ คือ digest และจำนวน hash ต่อการเรียกแต่ละครั้ง ซึ่ง test 114 ตัวตรวจไว้แล้ว ส่วนฝั่ง query จำนวน hash ตรงกันทุก query
- **ค่าบน Mac ต่ำกว่าบน cloud ทั้งหมด** ให้ดูที่อัตราส่วน

## เทียบความยุติธรรมกับ baseline

ตรวจโค้ดตรวจผลของทั้งสาม baseline หาจุดช้าแบบเดียวกัน:

| scheme | hash ใน Merkle / การตรวจ | ลูปซ้อน (`in list` ในลูป) |
|---|---|---|
| SE-COLLAB | `leaf_hash` / `node_hash` เรียก `sha256` ครั้งเดียวอยู่แล้ว · `H()` แบบหลาย update ใช้แค่ใน `result_digest` (1 ครั้งต่อผลลัพธ์) วัดแล้ว ถ้าปรับแบบเดียวกันได้ไม่ถึง 4% (3.55 → 3.41 ms ที่ rQ = 2,550) จึงไม่ต้องแก้ · `verify_multiproof` แบบ sort ทุกชั้นใช้เฉพาะ `proof_mode="multi"` ซึ่งไม่ได้ใช้ในผลที่รายงาน | ไม่มีในการตรวจ (ที่เจออยู่ในโค้ดสร้างการโจมตี ซึ่งไม่ถูกจับเวลา) |
| Du | `H` = `sha256` ครั้งเดียว · HMAC ใช้ `hmac.new` · กรองด้วย numpy | ไม่มีในการตรวจ (`fids` ในโค้ดสร้างการโจมตีเป็น set และอยู่นอกช่วงจับเวลา) |
| Chen | PRF ใช้ `hmac.digest` ครั้งเดียว · XOR ทั้งก้อนผ่าน int | ไม่มี |

**สรุป:** baseline ไม่มีจุดช้าแบบเดียวกันที่ควรแก้ การแก้ครั้งนี้ทำให้ AMTP มีต้นทุน hash ต่อครั้งพอๆ กับ baseline ไม่ได้ได้เปรียบ
