# รายงาน: Validator ช้าผิดปกติที่ b = 1000 — หาสาเหตุและแก้ (15 พ.ย. 2026)

## อาการ

ex3 (update cost) บน cloud แบบ γ มี v: ไฟล์ต่อ epoch เพิ่ม 10 เท่า แต่เวลาของ Validator เพิ่ม 78 เท่า

| | b = 100 | b = 1000 | เพิ่ม |
|---|---|---|---|
| posting ที่ต้องตรวจ (มี v) | 82k | 788k | 9.6× |
| CS (server) | 5.2 s | 34 s | 6.6× |
| **Validator (มี v)** | 7.6 s | **592 s** | **78×** |
| Validator (ไม่มี v) | 1.0 s | 16.3 s | 16× |

## หาสาเหตุ (cProfile, Mac, N = 100k, b = 1000, γ มี v, insert + delete 1 รอบ)

| ส่วน | เวลา |
|---|---|
| Validator ทั้งหมด | 869 s |
| **`_imt_root`** | **777 s (89%)** |
| ที่เหลือ (γ, proof, partition, ลายเซ็น) | ~92 s |

เวลาเกือบทั้งหมดอยู่ที่การตรวจ next pointer ของ IMT 2 จุดใน `amtp_code/amtp/validator.py` (`_imt_root`):

1. ทุก key ที่ถูกลบ ต้องมีใบที่ชี้มาหามัน (predecessor) — โค้ดเดิมไล่ดู**ทุกใบที่เปิด**สำหรับ**ทุก key ที่ถูกลบ** (generator ถูกเรียก 1,920 ล้านครั้ง)
2. ทุก key ใหม่ ต้องมีใบที่ครอบมัน (h < a < next) **พอดี 1 ใบ** — โค้ดเดิมไล่ดูทุกใบสำหรับทุก key ใหม่

ที่ b = 1000 แบบมี v มีใบที่เปิด ~4 แสนใบ คูณ key ใหม่ / ถูกลบหลักพัน → หลักพันล้านรอบ (O(n·m)) แบบไม่มี v มีใบที่เปิดแค่ ~17,000 จึงเห็นน้อยกว่า **เป็นปัญหาประสิทธิภาพของโค้ด ไม่ใช่ธรรมชาติของ scheme**

## แก้อะไร

ไฟล์เดียว `amtp_code/amtp/validator.py`: แยกสองการตรวจออกเป็นฟังก์ชัน

| ฟังก์ชัน | วิธีใหม่ | ต้นทุน |
|---|---|---|
| `check_removed_predecessors` | จด next pointer ทุกใบลง set ครั้งเดียว แล้วเช็กว่า key ที่ถูกลบอยู่ใน set | O(n + m) |
| `bracket_new_keys` | เรียงใบตาม h ครั้งเดียว เก็บ next ที่ใหญ่สุดและใหญ่อันดับสองของแต่ละ prefix; ใบที่ h < a คือ prefix (หาด้วย binary search); ครอบ ≥ 1 ใบ ⇔ next ใหญ่สุด > a, ครอบ ≥ 2 ใบ ⇔ next อันดับสอง > a ด้วย; ถ้าพอดี 1 ใบ ใบนั้นคือใบที่ next ใหญ่สุด | O((n + m) log n) |

- **เงื่อนไข ลำดับการตรวจ และข้อความ error เหมือนเดิมทุกตัว** ผลการตัดสิน accept / reject ไม่เปลี่ยน
- ไม่แตะ: สูตร hash / γ / ρ / IMT leaf / R_D, การตรวจ proof อื่น, server, ผู้ใช้, Root Anchor, baseline, รูปแบบ proposal

## หลักฐานว่าการตัดสินไม่เปลี่ยน

`amtp_code/tests/test_validator_imt_checks.py` (ใหม่, 61 test) เก็บโค้ดเดิมไว้เป็นตัวอ้างอิงแบบคำต่อคำ แล้วเทียบกับโค้ดใหม่:

- **กรณีเจาะจง:** π ไม่ส่ง predecessor ของ key ใหม่; π ไม่ส่ง predecessor ของ key ที่ถูกลบ; predecessor ผิดตัว; ครอบ 2 ใบ (ช่วงซ้อน, next เท่ากัน); key ตรงขอบช่วงพอดี (h หรือ next — ต้องไม่นับ); ช่วงกลับด้าน / ว่าง; ผิดทั้งสองจุดพร้อมกัน (ต้องรายงานจุด removed ก่อนเหมือนเดิม); input ว่าง — **ข้อความ error ต้องตรงตัวอักษร**
- **input สุ่ม 8,000 ชุด** (ลูกโซ่ปกติ และ next pointer มั่ว, ค่าซ้ำ / ชนขอบเยอะ): ผลต้องเท่ากันทุกชุด (accept + ใบที่ครอบเดียวกัน หรือ error ข้อความเดียวกัน)
- **end-to-end ผ่าน `Validator.check` จริง:** history ที่ถูกต้อง (b = 1, 5, 20) ผ่านทุก epoch ด้วยทั้งสองเวอร์ชัน; proposal ที่ถูกแก้ (ตัดใบ neighbour, ใส่ next ผิด, เปลี่ยนค่าใดๆ ใน π แบบสุ่ม) ได้ผลเท่ากันทุกกรณี
  - หมายเหตุ: ถ้าแค่ตัดใบออกจากหลักฐาน จะถูก reject ก่อนถึงสองจุดนี้ ที่ "IMT opening does not match R^idx" เพราะ proof ของ IMT ไม่ตรง สองจุดที่แก้กันกรณีที่ใบถูกเปิดอย่างถูกต้องแต่ไม่ใช่ใบที่ควรเป็น ซึ่ง test ระดับฟังก์ชันครอบคลุม
- **ลองใส่บั๊กเพื่อดูว่า test จับได้:** เปลี่ยน "พอดี 1 ใบ" เป็น "อย่างน้อย 1 ใบ" → fail 41 test; ปิดการตรวจ predecessor ของ key ที่ถูกลบ → fail 44 test (คืนโค้ดแล้ว)
- pytest ทั้งชุด 219 test ผ่าน ทั้งโหมดปกติและ `AMTP_GAMMA_V=0`
