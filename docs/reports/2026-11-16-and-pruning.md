# AND pruning (`--and-prune`) และตรวจ part เฉพาะไฟล์ผลลัพธ์ (`--part-results`)

วันที่ 16 พ.ย. 2026 · branch `feat/and-pruning`

## ทำอะไร

เพิ่ม AND pruning เป็น flag เสริม **ค่าเริ่มต้นปิด** ถ้าไม่เปิด flag ทุกอย่างทำงานเหมือน ASPA เดิมใน paper ผลเดิมทั้งหมดจึงไม่เปลี่ยน

**ปัญหา:** ตอนนี้เวลา query และขนาด proof โตตาม kQ และ N เพราะ server ส่ง posting list **เต็ม**ของทุก keyword และผู้ใช้ต้องตรวจ partition ทุกอันที่ list เหล่านั้นแตะ ทั้งที่ผลลัพธ์ของ AND มักมีแค่ไม่กี่ไฟล์

**หลักคิด:** ไฟล์ที่ตรงกับ AND ต้องอยู่ใน list ของ keyword ทุกตัว จึงต้องอยู่ใน partition ของ keyword ที่สั้นที่สุด (เรียกว่า focus set F) server จึงส่ง:
1. **list เต็มของ keyword ที่สั้นที่สุด:** ตรวจด้วย γ, ρ และ IMT เหมือนเดิม
2. **keyword อื่นส่งแค่ส่วนใน F (รูปแบบ `focus`):**
   - component ของ keyword นั้นในทุก partition ของ F ที่มี (`segs`)
   - ใน partition ของ F ที่ keyword นั้นไม่มี ให้ส่ง γ leaf สองตัวที่ติดกันซึ่งคร่อม PID นั้น (`nb` ส่งเป็น preimage คือ PID, v, H(Enc(L)))
   - ทั้งหมดเปิดด้วย multiproof เดียวใน R^post ของ keyword นั้น แล้ว ρ = H(h ‖ |Sel| ‖ R^post) ต้องอยู่ใน IMT เหมือนเดิม

**ไม่ต้องเปลี่ยน index, DO หรือ Validator:** ρ ผูก γ ที่เรียงตาม PID ไว้แล้ว และ Validator ตรวจทุกการเพิ่ม component ด้วย neighbour ว่าอยู่ในลำดับ PID (`validator.py` ส่วน `ins` / `pre`) การใช้ leaf สองตัวที่ติดกันพิสูจน์ว่า keyword ไม่มี component ใน partition จึงใช้ได้ HANDOFF §9 ข้อ D เคยเขียนว่าต้องเปลี่ยนโครงสร้าง index แต่จากที่ทำจริงไม่ต้อง

## ทำไมยังปลอดภัย (การจับ tamper ยังเท่าเดิม)

- **ผู้ใช้คำนวณ F เอง:** ใช้กฎ `boolean.focus` กับ keyword ที่ได้มาแบบเต็มและ keyword ที่พิสูจน์แล้วว่าไม่มีในระบบ กฎคือ AND ใช้ intersection และ OR ใช้ union ถ้า OR มีลูกตัวใดที่ไม่รู้ partition ผลคือ "ไม่มีขอบเขต" ในกรณีที่ไม่มีขอบเขต ถ้า server ส่งแบบ `focus` มา ผู้ใช้จะปฏิเสธ (check papc)
- **ตรวจว่าครอบคลุม F ครบ:** keyword แบบ `focus` ต้องมี component ในทุก partition ของ F หรือมี leaf ที่ติดกันคร่อม PID นั้น ถ้าไม่ครบ ผู้ใช้จะปฏิเสธ
- **ผลของ AND ยังถูกต้อง:** ไฟล์ที่ตรง B_Q ทุกไฟล์อยู่ใน F และใน F ผู้ใช้เห็น posting ครบทุก keyword ส่วนนอก F ข้อมูลที่เห็นเป็นเพียงส่วนย่อยของความจริง Eval เป็น monotone จึงสร้างผลเกินมาไม่ได้ ดังนั้น M̂_Q = M_Q
- **ไม่ต้องเชื่อว่า server เลือก keyword ที่สั้นที่สุดจริง:** ถ้า server เลือกผิด proof จะใหญ่ขึ้นเท่านั้น ผลยังถูกต้อง
- **check อื่นไม่เปลี่ยน:** ct, comp, part, anchor และ ctx เหมือนเดิม ทุกการ accept ยังผ่าน hash, Merkle หรือลายเซ็น
- **OR ไม่ถูก prune:** ต้องใช้ทุก list แบบเต็ม จึงได้ proof แบบเดิม

## เพิ่มเติม: ตรวจ part เฉพาะไฟล์ผลลัพธ์ (flag `--part-results`)

flag แยกจาก pruning ค่าเริ่มต้นปิด ใช้คู่กันหรือใช้แยกกันก็ได้ ผู้ใช้รับได้ทั้งสองรูปแบบเสมอ

**สิ่งที่เปลี่ยน:**
- **ตอนนี้:** server เปิด slot ของ**ทุกไฟล์ที่ posting แตะ** (M_cov) ในทุก partition ที่เกี่ยว แล้วเปิด H(PID ‖ v ‖ R_P) ของทุก partition เหล่านั้นใน domain tree
- **เมื่อเปิด flag:** server เปิด slot และ domain leaf **เฉพาะไฟล์ที่เป็นผลลัพธ์** (M_Q) ส่วน partition อื่นที่ posting แตะ ส่งเฉพาะ (PID, v) เป็น list ธรรมดา (`proof.versions`) เพราะผู้ใช้ต้องใช้ v คำนวณ γ

**ทำไมยังปลอดภัย:**
1. **posting ทุกรายการถูกยืนยันโดย PAPC อยู่แล้ว:** ข้อมูล (cid, PID, ℓ) ทุกตัวอยู่ใน γ และผูกต่อไปถึง ρ, IMT, R^idx และ root ที่ anchor ไว้ ถ้าแก้ posting γ จะไม่ตรง จึงไม่ต้องพึ่ง partition tree ในการยืนยัน posting
2. **v ใน list ธรรมดาถูก γ ผูกไว้:** γ = H(PID ‖ v ‖ H(Enc(L))) ถ้า v ผิด γ ที่ผู้ใช้คำนวณได้จะไม่อยู่ใน R^post และ ρ̂ จะไม่อยู่ใน IMT (test `test_wrong_plain_version_is_caught`) จุดนี้เป็นประโยชน์ของการมี v ใน γ
3. **ความสอดคล้องระหว่าง posting กับ partition:** Validator ตรวจตอน update ก่อน anchor ทุกครั้ง (Proposition 1)
4. **ไฟล์ผลลัพธ์ยังตรวจ part เต็ม:** ผู้ใช้คำนวณ M̂_Q = Eval(B_Q) เอง แล้วต้องมี descriptor ครบ**ทุก** partition ของ M̂_Q และไม่มีเกิน ส่วน `versions` ต้องเท่ากับ partition ที่เหลือพอดี ถ้าไม่ครบจะถูกปฏิเสธที่ check part
5. **check อื่นไม่เปลี่ยน:** ct, comp, anchor และ ctx เหมือนเดิม hide, inject, modify และ old_version จึงยังถูกจับเหมือนเดิม

- honest query ทั้งแบบมีและไม่มี pruning
- การโจมตีทุกแบบของ adversary ทั้ง AND และ OR
- v ผิด, v หาย หรือ v เกิน
- ย้าย partition ของผลลัพธ์ไปไว้ใน list ธรรมดา
- fuzz

## เพิ่มเติม: ทำให้ server เร็วขึ้น (แก้โค้ดอย่างเดียว ผลลัพธ์เหมือนเดิมทุก byte)

**ปัญหา:** profile (เปิดทั้งสอง flag, 440 query) พบว่าเวลาฝั่ง server ส่วนใหญ่หมดไปกับ 2 อย่าง:
1. คำนวณ H(Enc(L)) ของ neighbour ใหม่ทุก query (487k ครั้ง)
2. ไล่นับ posting ทุกตัวเพื่อดูขนาด ใน `_and_plan` และ `_full_bytes`

ค่าทั้งสองคำนวณไว้แล้วตอนสร้าง snapshot แต่ถูกทิ้งไป

**แก้:** เมื่อเปิด `--and-prune` snapshot (`index.py`) จะเก็บ H(Enc(L_j)) ของทุก component และจำนวน posting ของแต่ละ keyword ไว้ด้วย (`post_inner`, `post_count`) แล้ว server ใช้ค่านี้แทน ค่าเหล่านี้สร้างพร้อม index ไม่ได้ขึ้นกับ query ที่เคยมีมาก่อน จึงไม่ใช่ cache และไม่มีปัญหาเรื่อง cold/warm

**ยืนยันว่าไม่เปลี่ยน scheme:**
- **A/B บน state เดียวกัน** (D1, 100k ไฟล์) เทียบ `server.py` ก่อนแก้ (commit `bb6ba17`) กับหลังแก้: response เหมือนกันทุก byte **440/440 query** (Search 1.1 + query ที่ keyword พบบ่อยทั้งหมด) ข้อนี้ใช้ได้กับ**snapshot และกุญแจชุดเดียวกัน**เท่านั้น
- **ข้าม process ผลอาจต่างได้ทั้งโค้ดเก่าและโค้ดใหม่:**
  - ทุกครั้งที่รัน กุญแจ k_s ของ domain และ nonce ของการเข้ารหัสจะสุ่มใหม่ ทำให้ token h ของ keyword และ cid เปลี่ยน (ส่วนการวางไฟล์ลง partition ตรวจแล้วว่าเหมือนเดิมทุกครั้ง)
  - B_Q เรียงตาม h ถ้า keyword ที่สั้นที่สุดสองตัวมีจำนวน partition และจำนวน posting เท่ากันพอดี server จะเลือกตัวที่มาก่อนตาม h ซึ่งเปลี่ยนไปในแต่ละรอบ
  - ตัวอย่าง: F20_k15_04 มี "constitute" กับ "problem solving" ที่มี 19 partition และ 20 posting เท่ากัน แต่เป็นคนละชุด partition ผลคือรอบหนึ่งส่ง posting 80 รายการ (proof 50,176 B) อีกรอบส่ง 82 รายการ (proof 51,040 B)
  - ไม่กระทบความปลอดภัยหรือความถูกต้อง ผู้ใช้ยอมรับทั้งสองแบบและได้ผลลัพธ์เดียวกัน

  - **แก้แล้ว:** `_and_plan` ตัดสินกรณีเสมอด้วยข้อมูลเท่านั้น คือรายการ PID ที่เรียงแล้ว และจำนวน posting ต่อ partition ไม่ใช้ลำดับของ h ผลจึงเหมือนเดิมทุกรอบสำหรับไฟล์ชุดเดียวกัน

**ข้อ 1, `--and-greedy` (flag ใหม่ ค่าเริ่มต้นปิด ใช้คู่กับ `--and-prune`):**
- **วิธีเดิม:** server ส่งแบบเต็มแค่ keyword ที่มี partition น้อยที่สุดตัวเดียว
- **วิธีใหม่:** server ประเมินด้วยว่าถ้าส่ง keyword อีกตัวแบบเต็ม F จะหดเหลือ intersection และ keyword ที่เหลือจะเปิด γ น้อยลง ถ้าคุ้มก็ส่งเพิ่ม ทำซ้ำจนส่งเพิ่มแล้วไม่คุ้ม (`_grow_full` ใน `server.py`)
  - การประเมินใช้แค่ set intersection และขนาด component เฉลี่ย
  - ข้ามขั้นนี้เมื่อ F มีไม่เกิน 8 partition
- **ความปลอดภัย:** ผู้ใช้ตรวจด้วยกฎ focus เดิม ซึ่งรองรับ keyword แบบเต็มหลายตัวอยู่แล้ว (intersection)
- **test ใหม่:**
  - เคสที่ส่ง keyword ตัวที่สองแล้ว F หดจาก 16 partition เหลือ 1
  - honest query ทุกรูปแบบยังถูกยอมรับและได้ผลถูกต้อง

- ผู้ใช้คำนวณ γ ใน papc จาก byte ชุดเดียวกันเป๊ะ แต่ไม่ผ่าน wrapper `H()` ที่ต้องเช็กชนิดของทุกส่วน

## เพิ่มเติม: เวลาและ memory ของการสร้าง snapshot

**ทำไมต้องวัด:** ex3 ไม่ได้นับเวลาสร้าง snapshot (`finalize_update(..., snapshot=False)`) แต่ในระบบจริง server สร้าง snapshot ใหม่ทุก epoch เพื่อตอบ query ถ้าจะเปิด `--and-prune` จึงต้องรู้ราคาส่วนนี้

**ก่อนแก้ (D1, 100k):** เปิด `--and-prune` แล้วสร้าง snapshot ช้าลงจาก 22.1 s เป็น 36.3 s (+64%) ทั้งที่จำนวน hash เท่ากัน (12,611,038) วัดที่ 50k ด้วย `tracemalloc` พบว่า memory เพิ่ม +77% (521 → 924 MB)

**ต้นเหตุ (วัดแล้ว):** snapshot เก็บ R^post tree และ list ของ H(Enc(L)) ไว้สำหรับ**ทุก** keyword (1.08 ล้านตัวที่ 100k) cyclic GC ของ Python จึงต้องไล่ object เหล่านี้ซ้ำไปมาระหว่างสร้าง ถ้าปิด GC ระหว่างสร้าง (50k) ส่วนที่ช้าเพิ่มจะเหลือ +5.5% แทน +26%

**แก้ (`index.py`, `server.py`):**
1. **ปิด cyclic GC ชั่วคราวระหว่าง `DomainState._build()`:** snapshot มีแค่ dict, list และ bytes ที่ไม่มี reference วนกัน memory ยังถูกคืนด้วย reference counting ตามปกติ ข้อนี้ใช้กับทุกโหมด รวมทั้งตอนปิด flag
2. **เก็บข้อมูล R^post ไว้เฉพาะ keyword ที่มีตั้งแต่ `KEEP_MIN_PARTS = 3` partition:** keyword ที่เล็กกว่านั้นคำนวณตอน query (ไม่กี่ hash และไม่เก็บไว้ จึงไม่ใช่ cache)
3. **ข้ามการสร้าง focus evidence ของ keyword เล็กเมื่อแบบเต็มไม่มีทางใหญ่กว่า (`_full_is_no_larger`):** ใช้ lower bound ของขนาดแบบ focus ผลการเลือกจึงเหมือนเดิมทุก byte (test `test_full_list_shortcut_never_changes_the_choice`)

## ข้อจำกัด (ต้องบอกใน paper ถ้าใช้)

1. **ได้ผลดีเพราะลักษณะของ query ชุดนี้:** query สร้างจากไฟล์ต้นทาง keyword ที่หายากที่สุดจึงมีประมาณ 1 ไฟล์ ถ้าทุก keyword มีไฟล์เยอะ ต้นทุนจะโตตาม |L_min| ซึ่งเป็นขอบล่างตามธรรมชาติของการพิสูจน์ AND วัดจริงแล้วในหัวข้อ "query ที่ keyword ทุกตัวพบบ่อย" ถ้าทุก keyword มี df ≥ 200 AMTP + pruning แพ้ทุก baseline
2. **OR ไม่ได้ลด:** AND-of-OR และ OR-of-AND ลดได้บางส่วน แต่ยังไม่ได้วัด (Search 2.1)
3. **ตัวเลขเป็นของ Mac ไม่ใช่ cloud:** baseline (SE-COLLAB, Chen, Du) วัดบน cloud จึงยังเทียบตรงๆ ไม่ได้ ต้องรัน baseline บนเครื่องเดียวกัน หรือรัน AMTP `--and-prune` บน cloud
4. **server ใช้ memory เพิ่ม:** เมื่อเปิด flag snapshot ใช้ memory เพิ่ม +23–24% (100k: 1,030 → 1,279 MB) และเวลาสร้าง snapshot เพิ่ม +1–2% ดูหัวข้อ "เวลาและ memory ของการสร้าง snapshot"
5. **slot multiproof อาจใหญ่ขึ้นเล็กน้อย:** ใน partition ที่เปิด slot น้อยลง ต้องใช้ sibling hash มากขึ้น ใน test เล็กเจอกรณี +80 B แต่ในผลวัดจริงไม่มี query ไหนที่ proof ใหญ่ขึ้น
6. **ต้องแก้ paper และให้อาจารย์อนุมัติ:** ส่วน ASPA (eq. 52–57) และ proof ของ theorem ต้องเพิ่มรูปแบบ focus, ข้ออ้างเรื่องลำดับ PID ที่ Validator รับประกัน และกฎ focus
